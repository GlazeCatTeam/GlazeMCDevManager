# ADR-0008 每个功能先定义能力，并通过 MCP 对外部 AI 工具开放

- 状态：已接受
- 日期：2026-10-15
- 关联：取代 [PROJECT.md](../PROJECT.md) 决定 #2 中"不做 MCP"的部分

## 背景

用户要求设计每个功能时都考虑让外部 AI 工具（Claude Code、Codex、Cursor 等）通过 MCP 接入。应用本身仍不内置 AI。

如果功能只写在界面里，以后再补 MCP 就要把业务逻辑从界面里拆出来，每个模块都返工一次。

## 决定

1. **能力优先**：每个业务功能先在 `@glaze/contracts` 中定义为一个能力（RPC 方法），包含参数、返回值、权限、风险等级和面向 AI 的说明。界面、插件、MCP 都是这同一份能力的调用方，不允许出现"只有界面能做"的业务逻辑。
2. **MCP 服务内置在主进程**，由新包 `@glaze/mcp` 实现，把标注了 `mcp.expose` 的能力自动映射为 MCP 工具和资源。
3. **MCP 客户端是一种新的调用者身份**（`{ type: "mcp" }`），和插件一样走权限代理：需要用户在应用内配对授权，按权限授予，写操作需要应用内确认，全部写审计日志。
4. **凭据规则不变**：MCP 永远拿不到 Cookie、密码；登录、删除账号等凭据相关能力不对 MCP 开放。
5. 插件可以通过新贡献点 `tools` 贡献 MCP 工具，权限不超过插件自身权限。

## 后果

- 每个模块的工作量多一步：先写能力契约和 AI 说明，再写界面。换来的是界面和 MCP 天然一致，也更容易测试。
- 新增一个对外入口，攻击面变大，需要配对、权限、确认、审计和限流来控制。
- MCP 服务默认关闭，用户在设置里打开，避免没用到的人承担风险。
- 引入 `@modelcontextprotocol/sdk` 依赖。
